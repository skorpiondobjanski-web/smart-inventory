### ЗАВДАННЯ 2. АНАЛІЗ ТА ВИБІР СТРАТЕГІЇ РОЗГАЛУЖЕННЯ (BRANCHING STRATEGY)

Для організації командної розробки ВІС «SmartInventory» проведено порівняльний аналіз двох популярних стратегій розгалуження:

| Характеристика | GitFlow Strategy | GitHub Flow Strategy |
| :--- | :--- | :--- |
| **Основні гілки** | `main` (production), `develop` (staging). | Тільки `main` (або `master`). |
| **Допоміжні гілки** | `feature/*`, `release/*`, `hotfix/*`. | Тільки тимчасові `feature/*` або `bugfix/*`. |
| **Складність** | Висока (потребує суворого дотримання правил злиття). | Низька (ідеально для малих команд та швидких релізів). |
| **Безпека релізів** | Дуже висока (релізи проходять окрему гілку стабілізації). | Середня (код потрапляє в production відразу після Pull Request). |

#### Обґрунтування вибору: GitFlow Strategy
Для проєкту «SmartInventory» обрано стратегію **GitFlow**. Оскільки складські та фінансові системи є критично важливими бізнес-додатками, де будь-яка помилка в розрахунках собівартості FIFO може призвести до збитків, нам необхідний жорстко контрольований процес релізів.

**Схема розгалуження в проєкті:**
* `main`: містить виключно стабільний, протестований production-код. Кожен коміт позначається релізним тегом (наприклад, `v1.0.0`).
* `develop`: основна гілка інтеграції, куди зливаються всі розроблені фічі. Проходить постійне внутрішнє тестування (Staging).
* `feature/catalog-import`: гілка для розробки модуля імпорту товарів (відгалужується від `develop`, зливається назад в `develop` через Pull Request).
* `release/v1.0.0`: тимчасова гілка для передрелізного тестування, виправлення мінорних багів та формування документації перед злиттям у `main`.
* `hotfix/security-patch`: гілка швидкого виправлення критичних багів у production (відгалужується від `main` і після фіксу зливається одночасно в `main` та `develop`).

### ЗАВДАННЯ 3. ВИРІШЕННЯ КОНФЛІКТІВ ЗЛИТТЯ (MERGE CONFLICTS)

Конфлікт злиття виникає, коли два розробники змінюють однакові рядки в одному файлі в різних гілках, і Git не може автоматично визначити, які зміни зберегти.

#### 3.1. Симуляція конфлікту
Конфлікт виник у файлі конфігурації підключення бази даних `database.config.js`.
* У гілці `develop` розробник А вніс зміни:
  ```javascript
  const dbTimeout = 5000; // Збільшено таймаут для стабільності
  ```
* У гілці `feature/performance` розробник Б вніс зміни:
  ```javascript
  const dbTimeout = 2000; // Зменшено таймаут для швидкого відклику
  ```

При спробі злити `feature/performance` у `develop` за допомогою команди `git merge feature/performance` система видала помилку:
```text
Auto-merging database.config.js
CONFLICT (content): Merge conflict in database.config.js
Automatic merge failed; fix conflicts and then commit the result.
```

#### 3.2. Вирішення конфлікту
Git позначив конфліктні рядки у файлі `database.config.js` за допомогою маркерів конфлікту:
```javascript
<<<<<<< HEAD
const dbTimeout = 5000; // Збільшено таймаут для стабільності
=======
const dbTimeout = 2000; // Зменшено таймаут для швидкого відклику
>>>>>>> feature/performance
```

**Кроки вирішення конфлікту:**
1. Відкрито конфліктний файл у редакторі коду.
2. Проведено аналіз: спільно з командою вирішено встановити компромісний таймаут у 3000 мс.
3. Видалено маркери конфлікту (`<<<<<<<`, `=======`, `>>>>>>>`) та замінено код на компромісний:
   ```javascript
   const dbTimeout = 3000; // Оптимальний таймаут для бази даних
   ```
4. Додано виправлений файл до індексу та завершено злиття комітом:
   ```bash
   git add database.config.js
   git commit -m "Merge branch 'feature/performance' into develop. Resolved conflict in database.config.js"
   ```

### ЗАВДАННЯ 4. ВПРОВАДЖЕННЯ СЕМАНТИЧНОГО ВЕРСІОНУВАННЯ (SEMVER 2.0.0)

Для управління версіями випусків системи «SmartInventory» впроваджено міжнародний стандарт **Semantic Versioning 2.0.0 (SemVer)**. Версія має формат **MAJOR.MINOR.PATCH**:
* **MAJOR (Мажорна версія):** збільшується при внесенні зворотньо-несумісних змін API (наприклад, повна перебудова структури БД).
* **MINOR (Мінорна версія):** збільшується при додаванні нової зворотно-сумісної функціональності (наприклад, додано модуль Telegram-сповіщень).
* **PATCH (Патч версія):** збільшується при зворотно-сумісному виправленні помилок (багфіксів).
