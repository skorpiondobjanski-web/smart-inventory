## ПОРЯДОК І ЗМІСТ ВИКОНАННЯ ЗАВДАНЬ

### ЗАВДАННЯ 1. СТРУКТУРА СПЕЦИФІКАЦІЇ ВИМОГ (SRS)
Згідно з міжнародним стандартом IEEE 830-1998, специфікація вимог до системи управління запасами «SmartInventory» містить наступні ключові розділи:

#### 1. Вступ (Introduction)
* **1.1. Призначення (Purpose):** Цей документ визначає повний набір функціональних та нефункціональних вимог до ВІС «SmartInventory» версії 1.0. Документ призначений для команди розробників, спеціалістів з тестування (QA) та представників замовника.
* **1.2. Область застосування (Scope):** ВІС «SmartInventory» — це веб-орієнтована система для автоматизації складських операцій. Вона забезпечує реальний облік залишків, обробку прибутку/витрати, інтеграцію зі сканерами штрих-кодів, розрахунок собівартості за FIFO та автоматичні сповіщення. Система не містить вбудованих бухгалтерських інструментів розрахунку податків (для цього реалізується API інтеграція з 1C/BAS).
* **1.3. Скорочення та терміни (Definitions & Acronyms):**
  * **SKU (Stock Keeping Unit):** Унікальний артикул товарної позиції.
  * **Safety Stock:** Мінімальний страховий запас товару на складі.
  * **FIFO (First In, First Out):** Метод оцінки та списання запасів, за яким першими списуються товари, що надійшли першими.
  * **RBAC (Role-Based Access Control):** Рольова модель контролю доступу.

#### 2. Загальний опис (Overall Description)
* **2.1. Перспектива продукту (Product Perspective):** Система розробляється як самостійний продукт, що взаємодіє із зовнішніми системами (CRM, Інтернет-магазини) через відкритий RESTful API.
* **2.2. Функції продукту (Product Functions):**
  * Ведення каталогу SKU та категорій.
  * Облік транзакцій руху (Прихід, Витрата, Переміщення, Списання).
  * Інвентаризація залишків складу.
  * Розрахунок балансової вартості та аналітика обігу (ABC/XYZ).
  * Автоматичні сповіщення про дефіцит.
* **2.3. Класи та характеристики користувачів (User Classes):**
  * Комірник (висока інтенсивність використання, робота через термінали та ТЗД).
  * Завідувач складу (середня інтенсивність, робота на десктопах, аудит).
  * Менеджер з закупівель (середня інтенсивність, замовлення постачальникам).
  * Адміністратор (низька інтенсивність, конфігурація прав доступу).
* **2.4. Обмеження (Constraints):**
  * Розробка веб-додатку виключно за SPA-архітектурою.
  * СУБД має бути строго реляційною (PostgreSQL).
  * Обов'язкова робота системи на мобільних пристроях складських працівників.

### ЗАВДАННЯ 2. ДЕТАЛІЗАЦІЯ ФУНКЦІОНАЛЬНИХ ВИМОГ (USE CASE SPECIFICATIONS)
Для деталізації функціоналу системи розроблено специфікації двох критичних прецедентів використання.

#### Специфікація прецеденту 1: «Проведення видаткової накладної (Списання/Продаж)»
* **Актор:** Комірник або Завідувач складу.
* **Передумови (Preconditions):** Користувач автентифікований у системі з роллю «Комірник» або «Завідувач складу». Склад зберігання обраний та активний.
* **Основний сценарій (Main Flow):**
  1. Користувач переходить у розділ «Документи» та натискає «Створити видаткову накладну».
  2. Система генерує унікальний номер документа та підставляє поточну дату й час.
  3. Користувач додає товарні позиції до табличної частини накладної (шляхом введення SKU вручну або зчитування сканером штрих-коду).
  4. Користувач вказує кількість для кожної позиції.
  5. Система автоматично розраховує проміжну та загальну вартість документа на основі цін продажу.
  6. Користувач натискає кнопку «Провести документ».
  7. Система перевіряє поточні залишки на обраному складі для кожного товару.
  8. Система списує товари зі складу, оновлює кількісні залишки в реальному часі.
  9. Система фіксує успішне проведення документа, змінює його статус на «Проведено» та блокує від подальшого редагування.
  10. На екрані з'являється друкована форма накладної.
* **Альтернативний сценарій (Alternative Flow - Недостатня кількість):**
  * 7a. Якщо кількість будь-якого товару в накладній перевищує фактичний залишок на складі, система зупиняє проведення.
  * 7b. Система виводить червоне попередження: *«Помилка проведення: недостатня кількість товару [Назва SKU] (в наявності: X, запит: Y)»*.
  * 7c. Статус документа залишається «Чернетка», зміни в залишки складу не вносяться.
* **Постумови (Postconditions):** Баланс товарів на складі зменшено на вказані кількості. Документ проведений та захищений від редагування.

#### Специфікація прецеденту 2: «Автоматичне формування замовлення постачальнику (Low-Stock Alert)»
* **Актор:** Менеджер з закупівель (або автоматичний системний тригер).
* **Передумови:** Поточна кількість товару на складі впала нижче встановленого значення `safety_stock` (мінімального залишку).
* **Основний сценарій:**
  1. Система щогодини на фоновому рівні перевіряє залишки товарів на складах.
  2. При виявленні позиції, де `actual_stock < safety_stock`, система додає цю позицію до реєстру критичного дефіциту.
  3. Система автоматично ініціює створення документа «Замовлення постачальнику» у статусі «Чернетка».
  4. Система визначає основного постачальника для цього SKU (на основі історії попередніх успішних поставок) та підставляє його в документ.
  5. Розраховується оптимальна кількість для замовлення: `reorder_qty = safety_stock * 2 - actual_stock`.
  6. Менеджер з закупівель отримує сповіщення (E-mail / Telegram) про сформовану чернетку замовлення.
  7. Менеджер переходить до системи, відкриває чернетку замовлення, перевіряє ціни та натискає «Відправити постачальнику».
* **Постумови:** Чернетка замовлення створена, постачальник визначений, менеджер сповіщений.

### ЗАВДАННЯ 3. СПЕЦИФІКАЦІЯ НЕФУНКЦІОНАЛЬНИХ ВИМОГ

Вимоги до якості системи SmartInventory класифіковано за трьома основними напрямками та деталізовано у вигляді таблиці:

| Категорія вимог | Код вимоги | Опис вимоги | Метрика / Критерій перевірки |
| :--- | :--- | :--- | :--- |
| **Продуктивність (Performance)** | NFR-PER-01 | Час відгуку API на запити пошуку та фільтрації товарів. | < 0.8 с при обсязі бази даних до 500 000 SKU. |
| | NFR-PER-02 | Час обробки транзакцій при проведенні накладної (списання, FIFO). | < 1.5 с на документ обсягом до 150 рядків. |
| | NFR-PER-03 | Одночасне навантаження на систему. | Стабільна робота при 150 паралельних сесіях користувачів. |
| **Надійність (Reliability)** | NFR-REL-01 | Доступність веб-сервісу для користувачів. | Коефіцієнт готовності системи (Availability) >= 99.9%. |
| | NFR-REL-02 | Періодичність резервного копіювання даних. | Автоматичний бекап БД PostgreSQL кожні 24 години (вночі). |
| | NFR-REL-03 | Час відновлення після збоїв (Disaster Recovery). | Відновлення з хмарного сховища резервних копій < 1.5 години. |
