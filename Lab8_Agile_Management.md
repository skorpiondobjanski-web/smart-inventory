## ПОРЯДОК І ЗМІСТ ВИКОНАННЯ ЗАВДАНЬ

### ЗАВДАННЯ 1. АНАЛІЗ ТА ВИБІР МЕТОДОЛОГІЇ УПРАВЛІННЯ ПРОЄКТОМ

Для розробки ВІС «SmartInventory» було проаналізовано дві основні гнучкі методології:
1. **Scrum:** Жорстко структурований фреймворк, орієнтований на фіксовані за часом ітерації (Спринти тривалістю 2 тижні). На початку спринту команда фіксує перелік завдань з беклогу, які зобов'язується виконати. Учасники щодня збираються на Daily Scrum, а наприкінці проводять демонстрацію (Demo) та ретроспективу (Retrospective).
2. **Kanban:** Менш структурована методологія, орієнтована на безперервний потік задач. Немає фіксованих ітерацій, завдання додаються по мірі необхідності. Головне правило Kanban — обмеження обсягу незавершеної роботи (WIP - Work In Progress Limits) для запобігання перевантаженню команди.

#### Обґрунтування вибору: SCRUM
Для проєктування та первинної розробки системи «SmartInventory» обрано методологію **Scrum**. Оскільки система будується з нуля, фіксовані двотижневі спринти дисциплінують команду, дозволяють чітко розпланувати інкременти продукту та надавати замовнику працюючі модулі кожні 2 тижні.

### ЗАВДАННЯ 2. НАПИСАННЯ ІСТОРІЙ КОРИСТУВАЧІВ (USER STORIES)

Функціональні вимоги до системи представлено у вигляді історій користувачів (User Stories) за класичним шаблоном: **«Як [хто], я хочу [що], щоб [навіщо]»** з обов'язковим додаванням критеріїв приймання (**Acceptance Criteria** за шаблоном Given-When-Then).

#### User Story US-001: Автоматичне сповіщення про критичний залишок
* **Історія:** *Як менеджер з закупівель, я хочу отримувати автоматичні попередження, коли кількість товару на складі стає меншою за страховий запас, щоб я міг вчасно зробити дозамовлення та уникнути дефіциту.*
* **Критерії приймання (Acceptance Criteria):**
  * **Given (Дано):** Товар "Процесор Intel Core i9" має встановлений страховий запас `safety_stock = 5` одиниць. Його поточний залишок на складі становить 6 одиниць.
  * **When (Коли):** Комірник проводить видаткову накладну на відвантаження 2 одиниць цього товару.
  * **Then (Тоді):** Поточний залишок стає 4 одиниці. Система негайно змінює статус товару на «Low Stock» (візуальний червоний індикатор на екрані) та відправляє сповіщення на E-mail/Telegram менеджера протягом 5 хвилин.

#### User Story US-002: Списання залишків методом FIFO
* **Історія:** *Як завідувач складу, я хочу, щоб система автоматично списувала собівартість товарів за методом FIFO при проведенні видаткових документів, щоб балансова звітність складу була фінансово точною.*
* **Критерії приймання:**
  * **Given:** На складі є дві партії одного товару: Партія А (10 шт. по 100 грн) та Партія Б (5 шт. по 120 грн).
  * **When:** Менеджер проводить видатковий документ на продаж 12 шт. товару.
  * **Then:** Система списує 10 шт. за ціною 100 грн та 2 шт. за ціною 120 грн. Загальна списана собівартість становить 1240 грн. На складі залишається 3 шт. товару з Партії Б за ціною 120 грн.

### ЗАВДАННЯ 3. ОЦІНКА ТРУДОВИТРАТ (STORY POINTS & PLANNING POKER)

Оцінка складності User Stories проводилася командою за допомогою методики **Planning Poker** з використанням шкали чисел Фібоначчі (1, 2, 3, 5, 8, 13, 21) для визначення відносних оцінок складності — **Story Points (SP)**. Story Points враховують три фактори: обсяг роботи, складність логіки та ризики/невизначеність.

#### Результати оцінки завдань Беклогу (Product Backlog):
1. **US-003 [Створення картки товару та каталогу SKU]:** Оцінка: **3 SP**. *(Низькі ризики, стандартні CRUD-форми)*.
2. **US-004 [Авторизація користувачів та рольова модель RBAC]:** Оцінка: **5 SP**. *(Середня складність, безпека потребує ретельної інтеграції JWT)*.
3. **US-005 [Проведення накладних з миттєвим оновленням залишків]:** Оцінка: **8 SP**. *(Висока складність, робота з транзакціями бази даних, паралельні запити)*.
4. **US-002 [Списання залишків методом FIFO]:** Оцінка: **8 SP**. *(Складні математичні розрахунки, облік партій, ризик помилок при великій кількості даних)*.
5. **US-001 [Автоматичні сповіщення Low-Stock]:** Оцінка: **5 SP**. *(Потребує налаштування черги фонових перевірок та інтеграції з API Telegram/SMTP)*.

### ЗАВДАННЯ 4. ОРГАНІЗАЦІЯ KANBAN-ДОШКИ ТА ПЛАНУВАННЯ СПРИНТУ 1

Для управління потоком задач та візуалізації прогресу розробки «SmartInventory» використовується Kanban-дошка із чотирма основними колонками. Для колонки «In Progress» встановлено ліміт WIP = 3 для запобігання перевантаженню розробників.

#### Розподіл завдань під час Спринту 1 (Тривалість: 2 тижні, сумарна ємність команди: 24 SP):

```
+-----------------------------------------------------------------------------------------+
|                                    SCRUM KANBAN BOARD                                   |
+---------------------+---------------------+---------------------+-----------------------+
|  BACKLOG (Беклог)   |    TO DO (Планується)|IN PROGRESS (WIP: 3)|     DONE (Готово)     |
+---------------------+---------------------+---------------------+-----------------------+
| US-001 [Low-Stock]  | US-002 [FIFO]       | US-004 [RBAC]       | US-003 [Product CRUD] |
| (5 SP)              | (8 SP)              | (5 SP)              | (3 SP)                |
|                     |                     |                     |                       |
|                     |                     | US-005 [Transactions|                       |
|                     |                     | (8 SP)              |                       |
+---------------------+---------------------+---------------------+-----------------------+
```

* **DONE (Готово):** Створено базовий каталог товарів та категорії (US-003, 3 SP) — завдання повністю завершене та пройшло тестування.
* **IN PROGRESS (В роботі):** Реалізація рольового доступу JWT (US-004, 5 SP) та розробка логіки складських накладних (US-005, 8 SP). Обидві задачі знаходяться на етапі активного кодування та модульного тестування.
* **TO DO (В черзі спринту):** Реалізація алгоритму FIFO (US-002, 8 SP) — задача запланована на другий тиждень спринту.
* **PRODUCT BACKLOG (Поза спринтом):** Задача автоматичних сповіщень (US-001, 5 SP) перенесена на наступний Спринт 2, оскільки сумарна ємність поточного спринту завантажена.
